## Q1 · velRMS 的頻段與 ISO Zone 邊界是否相容 → **可接受**

**背景**：ISO 10816-3 的分區定義在 10–1000 Hz（> 600 rpm）或 2–1000 Hz
（120–600 rpm）的速度 RMS 上。我方以頻域積分（10–1000 Hz）對照前端 velRMS，
比值 1.09–1.16——量綱正確，但這 9–16% 的落差代表前端濾波帶與標準不同，
而前端的濾波設定取不到。

**結論**：專家確認在「篩選預警」的定位下可接受，不需要向前端要濾波設定，
也不需要自行從原始波形重算。

**程式**：無變更。維持以前端 velRMS 直接對照 ISO Zone 邊界。

**要記住的限制**：邊界附近的設備（例如 Group 2 剛性基礎的 A/B 界 1.40 mm/s）
仍可能因這 9–16% 的差異跨區。若日後出現「Zone 判定與現場實測不符」的個案，
這是第一個要回頭檢查的地方。

## Q2 · kurtosis 在本廠沒有鑑別力 → **移除 kurtosis 通道**

**背景**（兩項實測）：

1. **跨設備反向**——三台設備 accOA 1137.6/504.8/129.7 對應 accKURT 中位數
   2.37/3.60/4.53，排序完全顛倒。成因是 kurtosis 為比值型指標
   （Pearson 定義 m₄/m₂²），分母含背景振動量：機器越吵，σ 越大，偶發衝擊
   越被稀釋。受控驗證可重現此型態——固定衝擊列、只調背景雜訊，accOA 上升
   8 倍時 accKURT 由 22.8 降至 3.0。
2. **改成純相對基準後仍無鑑別力**——移除失效的絕對門檻、聚合改用中位數後，
   觸發結果完全沒變（33 週 511 次 / 60 台，佔機隊 88%），且門檻掃描曲線
   平滑無斷崖（1.5→4.0 件數 −46%、告警總天數僅 −22%）。

**結論**：kurtosis 不作為衝擊判準。

**程式變更**：

| 位置 | 變更 |
|---|---|
| `vibcore/rules/metric_rules.py` · `_IMPACT_CHANNELS` | 移除 `kurt` / `kurt_axis` 兩個通道 |
| `vibcore/rules/metric_rules.py` · `impact_rise()` | 只判定 `crest` 與 `crest_axis`；連帶移除 `require_both` 參數（它原本是用來要求 crest 與 kurt 同步上升） |
| `vibcore/rules/metric_rules.py` · `_DEGRADE_TREND_METRICS` | 移除 `acc_kurt`——「數值上升＝惡化」這個前提在本廠不成立 |
| `validate/rule_defaults.py` | IMPACT_RISE 參數只剩 `crest_sigma` / `crest_axis_sigma` |
| `validate/rules_stub.py` | 同步改成 crest-only，免得退回 stub 時與真實實作結果不同 |

**刻意沒有變更的部分**：

- **`STEP_CHANGE` 仍使用 `acc_kurt`**。在那裡它的角色是「這台機器的運轉點
  是否偏離自己的常態」的其中一個維度，不是衝擊判準；而且移除會改變
  Mahalanobis 的維度與門檻語意（k 維距離平方服從卡方分布，自由度變了，
  同一個門檻數字對應的稀有程度就不同）。這不在本次定案範圍內。
- **accKURT 欄位仍照常聚合入庫**（`acc_kurt` / `acc_kurt_median` /
  `acc_kurt_axis_max` / `acc_kurt_axis_median`）。不做破壞性 migration——
  STEP_CHANGE 還在用，且日後若換感測器或前端改算法需要重新評估。

**accCREST 為什麼留著**：它同樣是比值型指標（peak/RMS），但沒有對應的
實測證據顯示它在本廠失效，且它是諧波不可用之後僅存的衝擊性通道。

移除 kurtosis 後的實測（66 台 · 11 週 · 2026-06-05 起）：IMPACT_RISE 從
511 次 / 60 台（88% 機隊）降到 **144 次 / 37 台（56%）**。更關鍵的是門檻
掃描的行為變了——舊版調緊門檻幾乎不減少告警時間（件數 −46%、天數只
−22%、平均天數 4.3→6.2 天上升，是事件被合併的徵象），新版件數與天數
同比例下降（−81% / −82%）、平均天數維持 1.6 天不動。**門檻從「調了沒用」
變成一個真的旋鈕**，這是這次改動最實在的效果。

### STEP_CHANGE 要不要也拿掉 acc_kurt → **不拿掉**（2026-09-24 對照回測）

同一批資料（66 台 · 11 週）跑兩輪，唯一差別是 STEP_CHANGE 的特徵集，
門檻依卡方等效值對齊（k=4 的 3.0 ↔ k=3 的 2.71，尾機率皆 0.061）：

| 尾機率 | A：k=4 門檻 / 件數 / 天數 | B：k=3 門檻 / 件數 / 天數 | 件數差 | 天數差 |
|---|---|---|---|---|
| 0.406 | 2.0 / 343 / 1370 | 1.71 / 334 / 1379 | −2.6% | +0.7% |
| 0.181 | 2.5 / 289 / 1043 | 2.21 / 277 / 1025 | −4.2% | −1.7% |
| **0.061** | **3.0 / 246 / 818** | **2.71 / 228 / 801** | **−7.3%** | **−2.1%** |
| 0.0156 | 3.5 / 183 / 655 | 3.22 / 179 / 652 | −2.2% | −0.5% |
| 0.0030 | 4.0 / 148 / 553 | 3.73 / 140 / 538 | −5.4% | −2.7% |
| 0.00005 | 5.0 / 101 / 440 | 4.75 / 94 / 424 | −6.9% | −3.6% |

作業點的影響台數：**51 台 → 50 台**。

判讀規則是**在看到結果之前**訂的：影響台數要差 8 台以上（51 → 43 以下）
才算「明顯」，差不多就維持現狀、不為了改而改。實測差 1 台，因此維持
四特徵不變。

**這個測試能證明什麼、不能證明什麼**（重要，別過度解讀）：

- 能排除的：acc_kurt 在 STEP_CHANGE 裡**沒有攜帶重要的獨有訊號**。
  若有，拿掉它應該會讓 B 明顯漏掉一些設備，但沒有。
- 不能分辨的：「它是噪音」與「它只是跟其他三個特徵重複」。因為對齊
  尾機率等於把兩邊的誤報率**按定義**固定成一樣，所以在不知道哪些觸發
  是真的情況下，這兩種情形都會給出相同的件數。這是這個測試設計本身的
  限制，不是資料不足。

要再往下分辨，唯一便宜的做法是比對兩輪 `episodes_detail.csv` 的設備清單：
若 B 的 50 台是 A 的 51 台的子集，就是單純的重複；若兩邊各有對方沒有的
設備，代表 acc_kurt 會改變「誰被標記」，那就值得再看。目前未做。

## Q3 · 是否必須做工況分層 → **納入，但細節待討論**

**結論**：可額外提供 mapping CSV，電流與頻率一同納入。實際欄位格式與
分層方式尚待討論。

**第一階段已完成**（2026-09-25）：對應與載入層。分層演算法仍未定案——
兩者刻意分開，因為分層怎麼切要先回答「velRMS 到底有沒有隨轉速變化」，
而那是接上 SCADA 之後才驗得了的事。

| 位置 | 內容 |
|---|---|
| `vibcore/io/scada.py` | tag 對應表解析、讀值解析、有效樣本數換算、與每小時聚合的時間對齊 |
| `vibcore/db/repository.py` | `upsert_tag_mappings` / `get_tag_mappings` / `bulk_insert_scada` / `get_scada` |
| `validate/scada_setup.py` | `emit`（產範本）／`check`（檢查填寫）／`probe`（實測刷新週期） |

**`Label` 欄已經帶著 tag 名稱**：實測 `ZP 3-5_M1` →
`FACCIMTAB.ZONE1_K12_CHS|K12_BF_CHS_ZP350_INV_I`（`_INV_I` 看起來是變頻器
電流），但不是每台都有。`emit` 會把它預填進去，並在 note 欄標註「請確認
確實是電流」——型別是從命名猜的，猜錯會讓整個分層用到錯的變數。

**兩個關鍵設計**：

1. **有效樣本數不等於列數。** 檔案每 2 分鐘一列，但值約 15 分鐘才真的
   更新，連續數列是同一個值。直接拿列數當樣本數會高估約 7 倍，任何以它
   為分母的統計（標準差、信心度、分層後每層夠不夠樣本）都會失真。
   `effective_sample_count()` 就是為了不讓這件事被忘記而存在；`probe`
   子命令會拿實際讀值量出「值真正變動的間隔」，與程式假設不符時會提醒改常數。
2. **過期值有容忍上限（20 分鐘）。** 沒有上限的話，SCADA 斷線兩小時期間
   的每一個振動樣本都會被貼上斷線前那一筆值，整段被分到錯的工況，
   而且不會有任何錯誤訊息——與備機旗標被覆寫是同一類的安靜失效。
   超過容忍窗一律留 NaN（工況未知），不硬貼。

`variable_type` 限定 `current` / `frequency` / `power` 三種，其餘拒收且
不自動對應——猜錯會讓頻率被當成電流用，那比沒有資料更危險。

**下一步**（待資料）：用真實讀值跑 `probe` 確認刷新週期，再算 velRMS
對頻率的關係。若關係不明顯，分層就是在解一個不存在的問題。

**討論前需要釐清的**：

1. mapping CSV 的欄位長相——一台設備對幾個 tag？tag 名稱與 `device_id`
   怎麼對應（Analytic CSV 的 `Label` 欄目前存的就是電流 TAG 名稱，
   見 `validate/points._position_series` 的註解，可能已經是現成的對應）。
2. SCADA 讀值的取樣頻率與時間戳時區——要與 `measurement_agg` 的
   `ts_hour` 對齊才能分層。
3. 分層的切法：轉速區間？負載區間？至少幾層？代價是每層樣本數變少，
   而基準期本來就要求 14 天窗口內 168 小時可信資料。
4. 歷史資料的回補範圍——沒有歷史 SCADA 就只能從接上之後才開始分層，
   既有基準期要不要重算。

## Q4 · 備機的監測策略 → **先靜態旗標，之後改電流**

**結論**：mapping 帶一個備機欄位先讓 `is_standby` 有正確來源；等 SCADA
電流接上後改用電流判斷實際有沒有開機，靜態旗標退為 fallback。

**程式變更**（第一階段，已完成）：

| 位置 | 變更 |
|---|---|
| `vibcore/types.py` · `DeviceContext.is_standby` | `bool` → `bool \| None`，預設 `None`。三態：True/False 是台帳明確填寫，None 是「這個來源不知道」 |
| `vibcore/db/repository.py` · `upsert_device` | INSERT 用 `COALESCE(%(is_standby)s, FALSE)`（DB 欄位是 NOT NULL）；ON CONFLICT 用 `COALESCE(%(is_standby)s, device.is_standby)` 保留台帳值 |
| `validate/points.py` | 台帳沒填時給 `None` 而非 `False` |

**修掉的是什麼 bug**：每日排程用 Analytic CSV 組出的 `DeviceContext`
不可能知道備機與否，但舊版預設 `False`，upsert 時會把管理員設好的
`True` 重設為 `False`，**全程沒有任何錯誤訊息**。這也是回測中
`STANDBY_NO_RUNTIME` 觸發 0 次的原因之一。

ON CONFLICT 子句讀的是原始參數而不是 `EXCLUDED.is_standby`——`EXCLUDED`
取的是 VALUES 算完之後的值，那個 `COALESCE` 已經把 NULL 變成 FALSE，
用它就分不出「確認不是備機」與「不知道」了。

**第二階段（待 Q3 定案後）**：用電流判斷運轉狀態。這件事的 CP 值比工況
分層更高——目前「設備是否在運轉」是用 velRMS 門檻猜的，而那個分類是整套
涵蓋率統計的分母。

## D1 · 要不要補 ISO 台帳 → **需要補**

**依據**：未分類時 VEL_HIGH 退回相對基準 3σ，而那遠比 ISO 錨定門檻敏感
——不補台帳省下的是填兩個欄位的功夫，換來的是數倍的工作量。

### 驗收結果（2026-09-24，真實台帳）

同一批資料（66 台 · 11 週 · 2026-06-05 起）跑兩輪，唯一差別是有沒有帶
`--device-meta`：

| | A：無台帳 | D1：有台帳 | 變化 |
|---|---|---|---|
| VEL_HIGH 件數 | 117 | **41** | −65% |
| VEL_HIGH 影響台數 | 36 | **10** | −72% |
| 設備狀態類・進 SLA | 117 件（0.17 件/設備/週） | **42 件（0.06 件/設備/週）** | −64% |
| 全廠每週工作量 | 10.6 件 | **3.8 件** | **2.79×** |
| ISO_ZONE | 0 | 0 | — |
| ISO_CLASS_SUSPECT | 0 | **1 件 / 1 台** | 台帳生效 |
| STANDBY_NO_RUNTIME | 0 | **1 件 / 1 台** | 備機旗標生效 |

**補台帳有效，結論不變；但倍率要更正為 2.8 倍，不是先前一路引用的
4.3 倍。** 4.3 倍那個數字來自 33 週那一輪，當時的窗口含一月換版斷層
（涵蓋率僅 51.1%），斷線造成的資料稀疏會同時抬高未分類那一輪的 σ 判定
觸發量，把差距放大。乾淨窗口上的實測是 2.8 倍，應以此為準。

**ISO_ZONE 仍是 0 次，而且這次是好消息**：台帳確實生效了（VEL_HIGH 大幅
下降、ISO_CLASS_SUSPECT 與 STANDBY_NO_RUNTIME 開始觸發，三者都只有在
分類存在時才可能發生），所以 0 次代表「照 ISO 看，沒有設備達到 Zone C」
——這是正確的結論，不是判定失效。

**VEL_HIGH 的 σ 掃描仍有反應**（sigma 2.0→4.0：51→33 件），代表還有一部分
設備沒走 ISO 路徑、仍在 sigma_fallback。可能是台帳只填一半、device_id
對不上、或額定功率 ≤ 15 kW 被排除在適用範圍外。用
`python -m validate.iso_readiness --data-dir <資料夾> --device-meta <台帳>`
可以逐台分辨是哪一種。

**待追**：`ISO_CLASS_SUSPECT` 那 1 件。這條規則是在比對「基準期的實測
水準」與「台帳所填分類」是否矛盾，觸發代表兩者對不上——要嘛分類填錯
（最常見是 rigid/flexible 填反，邊界差近一倍），要嘛那台機器本身就有問題。
是台帳品質的第一個回饋，值得逐台確認。

**程式變更**（補台帳的路徑）：

| 位置 | 變更 |
|---|---|
| `validate/iso_readiness.py` | 新增 `--emit-ledger PATH`，產出待填 CSV 範本：預填 `device_id` / `rated_rpm` / `n_running` / velRMS 中位與 p95（判斷群組要看轉速與功率，判斷「這台有沒有在跑」要看運轉樣本數），空出六個待填欄位 |
| `validate/points.py` | `--device-meta` 除 `.json` 外新增 `.csv` 解析。空字串一律視為「沒填」而非「填了空值」；`is_standby` 接受 TRUE/true/Y/是/1 等寫法，認不得的值記警告並視為未填 |
| `validate/device_meta.example.json` | 改用 `iso_machine_group` / `iso_foundation`（舊的 `iso_machine_class` 是誤用 ISO 2372 時期留下的欄位），補上欄位說明 |

**為什麼是 CSV**：這份資料要由工程師填 68 台。逐台手寫 JSON 物件既慢又
容易漏逗號，錯一個字整份讀不進去；CSV 可以在試算表裡填、排序、整批複製
同型號的值。

**要填的六欄與填法**見 `validate/README.md` 的「需要準備什麼資料」。
重點：群組與基礎剛性**必須成對填**（只填一邊算不出 Zone，程式會整台視為
未分類）；同型號、同安裝方式可整批填；不必一次填到完美，
`ISO_CLASS_SUSPECT` 會回頭比對基準水準與所填分類是否矛盾。
