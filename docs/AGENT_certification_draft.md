# 1／8　Agent 目標定義 – 設備振動監測週報 Agent

## 專案說明

透過導入 Agent 協助設備振動監測的週報撰寫與異常追蹤。本系統以低成本三軸感測器做例行監測，
定位是**分流（triage）**：回答「哪幾台需要注意、有多急」，**不回答「是什麼故障」**——
深度診斷由既有的量測專家系統負責。

所有數值判定（ISO 10816-3 分級、相對基準偏離、趨勢、突變）皆由伺服器端的規則引擎以確定性
程式算完；Agent 讀取算好的結果、對照未結案事項與現場回覆，寫成工程師與主管看得懂的週報導讀。
確保異常被持續監看，並完成 Close Loop（觸發 → 判定 → 簽核回覆 → 規則校正）。

## Agent 指標

### 成功門檻設定

**成功條件：**
- 數字正確率 = **100%**（設計目標：以伺服器端數字白名單機制保證。⬜【待實作】，實作並實測前不宣稱）
- 診斷性斷言 = **0 件**（Agent 文字不得出現故障類型斷言、建議更換、剩餘壽命等用語）
- 嚴重度降級 = **0 件**（Agent 總評不得低於規則引擎依資料庫推算之嚴重度）
- 導讀判讀一致性 **≥ 80%**（Agent 判定的本期重點與分析人員一致。門檻沿用認證格式，【待與專家確認】）

**專案指標：**
- 效率指標：週報彙整時間減少 **> 70%**（現況工時【待實測】）
- 品質指標：未經事實包支持的數字或因果宣稱 = **0 件**

## Agent 代理角色 #1

代理資料分析人員（週報導讀撰寫與異常判讀）

## Agent 核心使命（代理職責）

- **日常維運**：每週自動判讀全廠設備的振動狀態與資料可信度，讓設備工程師與主管不用自己翻
  指標就能掌握本期重點與建議的下一步；有外部標準可引用的異常與系統事實自動進入事項（Finding）簽核流程並持續追蹤，
  相對變化類進入觀察名單（不派工），依現場回饋決定是否升級。
- **標準校正**：現場回覆（含確認的實際原因）累積成標籤資料，用於校正規則門檻與判準——讓標準隨
  現場實況演進，而不是固定不動。（轉手專家系統的判準與觀察名單升級門檻，已決議先試跑一陣子再定。）

## Agent 觸發時機

每週排程（日報選配）／異常事件　【排程時間待與平台設定確認】

## 驗證範圍

空調與冰水系統旋轉設備（冰水機、冰水泵、冷卻水泵、空調箱等）共 **66 台設備**，約 120 個三軸量測點
（含備機）。回測資料：2026-06-05 起 11 週。

## 工作流程

每日排程採集與小時聚合 → 規則引擎判定並建立事項 → 每週彙總 → Agent 判讀 → 伺服器端把關 →
週報產出 → 現場於 Dashboard 簽核回覆 → 持續追蹤與規則校正

## 流程圖描述

整個流程分為四個階段：

**Trigger（觸發） → Perception（感知）**
- 讀取未結案事項與工程師／主管的最後回覆（產報告前必先呼叫）
- 讀取本期彙總（資料涵蓋率、新發現／追蹤中／已解決／觀察名單）
- 讀取現行門檻設定（ISO 錨定門檻與規則參數）
- 下一輪重新感知

**Perception（感知） → Reasoning（推理）**
- 事項分類由系統依資料庫決定（新發現／追蹤中／已解決／觀察名單），Agent 不自行判斷
- 依涵蓋率決定結論的信心度；涵蓋率不足時不下定論
- 依事項狀態決定敘述詳略（已回覆未惡化 → 一行帶過；逾期或升級 → 拉高呈現）
- 同輪回饋

**Reasoning（推理） → Action（行動）**
- 彙整標準格式（總評 verdict／一句話 headline／建議動作 actions／補充 notes）
- 通過伺服器端把關（欄位型別與長度、HTML 轉義、每日上限；⬜ 診斷用語檢查、⬜ 數字白名單、⬜ 嚴重度下限）
- 寫入週報（排版與分段由系統負責，收件人與主旨由系統決定）

**Action（行動） → Feedback（回饋）**
- 現場人員於 Dashboard 依四階段簽核回覆（設備工程師 → 主管 → 專家複審 → 結案）
- 系統依 SLA 自動標示逾期與升級；數值回歸門檻內者由系統自動結案（與真人結案分開記錄）
- 回覆累積為標籤資料（含現場確認的實際原因），用於規則校正

# 2／8　Agent 資料來源與工具授權說明

## 資料來源（Data）

振動監測資料庫（PostgreSQL）——上游為前端感測系統輸出的逐秒 Analytic 檔，經每日 ETL
聚合為「每個量測點每小時一列」（同時完成運轉判定，停機時段不納入基準與判定）。
SCADA 電流／頻率資料目前為離線分析階段，**尚未納入判定**。

## 模型使用（Model）

地端 LLM（公司內部 AI 平台，模型與資料皆不出廠）

## 知識庫內容（Knowledge）

- 小時聚合指標（速度 RMS、加速度 RMS、波峰因子、位移 P2P、頻譜重心、溫度等）
- 設備台帳（ISO 10816-3 機器群組與基礎剛性、額定轉速、是否備機）
- 每個量測點自己的滾動基準（以該點基準期的中位數與離散度為準）
- 規則設定與現行門檻（ISO 錨定門檻、各規則的 σ 倍數與持續筆數）
- 未結案事項、現場回覆與簽核歷程、SLA 設定

## 工具／Skills 清單（Tool）

**對外 API：7 支唯讀 + 1 支寫入。** 下列 Skill 皆在**伺服器端**執行完畢，Agent 取得的是算好的結果，
不是原始資料。

| 分類 | Skills | Tools | Data | 狀態 |
|---|---|---|---|---|
| 感知 | 聚合與運轉判定 Skill | 逐秒資料壓成每小時；以速度 RMS（或電流）判定是否運轉，停機不納入 | 逐秒 Analytic 檔 | ✅ |
| 感知 | 滾動基準 Skill | 每個量測點以自己的基準期（14 天窗口、需足量可信小時）建立中位數與離散度；每台機器用自己的尺 | 該點歷史小時資料 | ✅ |
| 感知 | 管理標準 Skill | 以 ISO 10816-3（機器群組 × 基礎剛性）錨定門檻回答「這個數值算不算偏高」；未分類時退回相對基準並標示 | 設備台帳 + 規則設定 | ✅ |
| 感知 | 事件脈絡 Skill | 辨識哪些問題已在追蹤、現場與主管回覆過什麼，用進度語氣延續而非重複報告 | 未結案事項與回覆 | ✅ |
| 感知 | 資料可信度 Skill | 計算涵蓋率；區分感測器斷線、匯入未執行、設備未運轉（備機）三種「沒有資料」 | 小時資料狀態 + 匯入紀錄 | ✅ |

# 3／8　Agent 決策思維與流程

## Agent 任務與決策思維

| Tasks | 思考邏輯 | Tools / Skills |
|---|---|---|
| 承接歷史脈絡與管理標準 | 1. 先讀未結案事項與回覆再看數據，避免已回覆事項被當新問題重報<br>2. 區分靜態規則（門檻）與動態負債（未結案事項）<br>3. 引用門檻時只能引用工具查到的值，不用自身認知的業界標準 | • 事件脈絡 Skill<br>• 管理標準 Skill |
| 取得期間全域數據 | 1. 時間窗用相對天數（`days`），由系統換算成日曆日，**Agent 不自行計算日期**<br>2. 以系統彙整結果為準，不自行重算 | • 週報組裝 Skill |
| 健康形態與趨勢研判 | 1. 依事項家族決定敘述方向（波動型看形態、單調累積型看趨勢與信心度、事件型看狀態）<br>2. **涵蓋率不足時標示信心度，不下定論**<br>3. 「沒有警示」不等於「設備正常」：斷線期間不會產生警示<br>4. **不輸出故障類型判定**，只陳述現象與建議的下一步 | • 規則判定 Skill<br>• 趨勢與突變 Skill<br>• 資料可信度 Skill<br>• 滾動基準 Skill |
| 報告組裝與閉環追蹤 | 1. 三段式分段與次數由系統決定，Agent 不自行標注「第 N 次」<br>2. 帶齊定位欄位（對象類型／對象／事項類型）使敘述掛到對應事項卡片<br>3. **觀察名單不開行動項**（尚未達提報門檻，無負責人與期限）<br>4. 本期無異常則照實寫，不硬湊 | • 週報組裝 Skill<br>• SLA 與升級 Skill |

## Decision Flow

**觸發點 → Trigger：每週工作排程**
- Perception：取得未結案事項、本期彙總與涵蓋率、現行門檻

**事項分類（由系統依資料庫決定）**
- 新發現
- 追蹤中
- 已解決
- 觀察名單（規則觸發但未達提報門檻）

**是否有值得回報的事項？**
- 是 → 結構化內容
  - 依事項狀態決定詳略（見下）
  - 觀察到的現象與建議下一步分開寫；不指認故障類型
  - 沿用系統的追蹤帳本
- 否 → 照實寫「本期無異常」並標明涵蓋率，不硬湊

**伺服器端把關**（未通過即整份退回，不會出現在週報上）
- ✅ 欄位型別、列舉值、長度、禁止額外欄位
- ✅ HTML 轉義（樣板引擎 autoescape）
- ✅ 每日寄送上限與稽核紀錄
- ⬜ 診斷用語檢查（套用於 Agent 文字）
- ⬜ 數字白名單
- ⬜ 嚴重度下限

**寄出週報** → **事項追蹤回饋** → 回到事項分類

## 依事項狀態決定敘述詳略

| 事項狀態 | Agent 的寫法 |
|---|---|
| 主管已回覆且未惡化 | 一行帶過，說明現況與追蹤中 |
| 主管尚未回覆 | 重新提醒並給明確建議 |
| 已升級（escalated） | 不可輕描淡寫；寫出從基準值惡化到目前值的具體變化，提醒既有處置可能來不及 |
| 已逾 SLA | 主動點名，詢問新的時程 |
| 出現次數較多 | 語氣反映急迫性，不與第一次出現者同樣平淡 |

## 事項家族收斂分類

**波動型（oscillating）**：隨負載波動、會回落 → 以形態判準（持續超標 vs 零星尖峰）
- ISO 分級、速度 RMS 偏高、溫度上升

**單調累積型（monotonic）**：機械劣化不會自己回復 → 以趨勢與到達門檻的時間判準
- 衝擊性（波峰因子）上升、劣化趨勢、頻譜重心位移、軸向分布改變、多變量突變
- 目前此類規則為「觀察」等級，尚未達提報門檻者進入觀察名單，持續惡化越過門檻時由規則引擎自動升級

**事件型（event）**：二元狀態
- 感測器離線、資料品質、感測器飽和、安裝方向改變、備機長期未運轉、ISO 分類疑似填錯

## 閉環實際轉動的證據

### 一、規則校正閉環（離線回測 → 專家會議 → 規則調整 → 重跑驗證）已發生兩次

**(1) 衝擊性規則移除峰度（kurtosis）通道**
- 實測發現：三台設備的整體振動量 accOA 1137.6 / 504.8 / 129.7，對應峰度中位數 2.37 / 3.60 / 4.53，
  **排序完全顛倒**——峰度為比值型指標，機器越吵越被稀釋，在本廠沒有鑑別力。
- 專家會議決議：移除。
- 重跑結果（同一批 11 週資料；其餘七類規則的事件起訖逐筆相同，證明只有預期的規則變了）：
  衝擊性規則 **193 次 → 144 次（−25%）**，事件天數 426 → 231（−46%）；連帶的趨勢劣化規則 12 → 9
  （被拿掉的 3 筆判定指標都是峰度）。移除後為 144 次 / 37 個量測點（機隊 56%）。
  **移除的理由是指標本身沒有鑑別力，不是為了壓件數**——件數只少了約四分之一，不作為成效論點。
  （先前引用的「511 → 144」是 33 週對 11 週的錯誤比較，已更正；見
  `docs/DECISIONS_2026-09_expert_review.md` Q2。）
  門檻掃描的行為差異（舊版件數 −46%／天數 −22%，新版 −81%／−82%）仍待同視窗重做。

**(2) 補齊 ISO 設備台帳**
- 未分類時偏高規則退回相對基準 3σ，遠比 ISO 錨定門檻敏感。
- 補台帳後同一批資料：偏高件數 117 → **41**，影響台數 36 → **10**，全廠每週新增工作量
  10.6 → **3.8 件（2.8 倍）**。（更正紀錄：先前引用的 4.3 倍來自含換版斷層的窗口，已更正為乾淨窗口的 2.8 倍。）

> 這兩次都是**以實測數據改變系統判定規則**，同視窗對照均已完成：(1) 衝擊性規則 193 → 144（−25%）；
> (2) 偏高規則 117 → 41（每週工作量 2.8 倍）。
>
> 其後剩下的 41 筆全部來自額定 ≤ 15 kW、不在 ISO 範圍內的泵，又做了第三次調整：退回相對基準的路徑
> 加實用顯著性下限（41 → 19 筆），並降為觀察名單、**不派工**——沒有外部標準可引用就不派工。
> 下限數值是依分布選的起點，**不是專家定的標準**，由試跑回饋驗證。

# 7／8　設備振動監測週報 Agent Offline 驗證

## 驗證方法（本專案與 HVM 的差異，建議說明）

本專案週報**每週僅產出一次**，若採「上線後等待」，7 天僅能取得 1 筆樣本，不足以支撐成功率結論。
因此採**歷史期間回溯**：對過去逐週各自產生一份事實包，逐一交由 Agent 產生導讀並通過把關，取得多筆樣本。
所有資料均為該期間之**真實生產資料**，僅執行時間為一次補跑。

- 可用歷史：2026-06-05 起 **11 週**（66 台設備），預計取得 **11 份事實包**。
- 規則層已完成同一批資料的離線回測（見第 3 張閉環證據）；本張驗證的是 **Agent 導讀層**。

## 規則層離線回測（已完成，作為 Agent 導讀的輸入品質佐證）

| 項目 | 結果 |

## 附註：與 HVM 版本的刻意差異（建議於審查時主動說明）

**1. 正確率的性質不同**
HVM 以抽樣統計證明「測 N 次都對」；本專案的設計目標為**機制保證**——判定由規則引擎算完，
數字與診斷用語由伺服器端把關。**該機制目前尚未全部實作（見第 4 張），報告以實作與實測結果為準。**

**2. 樣本取得方式不同**
HVM 為日報，7 天即可累積足夠樣本；本專案為週報，故採**歷史期間回溯**產生多期樣本（預計 11 期）。
所有資料均為真實生產資料，僅執行時間為補跑。

**3. 全文去識別化**
本文件不含任何公司網域、IP 位址、主機名稱、人名或帳號——設備一律以類別（冰水機、冰水泵…）
或代號表示，事項以類型指認。可直接對外簡報。

**4. 本案的紅線是「不判定故障類型」**
本系統定位為篩選預警，資料不足以支撐故障診斷，因此**除了數字正確性之外**，另設診斷邊界護欄
（第 4 張 #5）：Agent 只能陳述現象與建議下一步，不得指認故障類型、建議更換零件或估計剩餘壽命。
這是本案相對於一般週報 Agent 最主要的額外風險控管。
