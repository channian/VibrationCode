# 前端資料契約

**用途**：界定本系統依賴前端匯出的哪些欄位、哪些不可信、哪些已廢棄。

**為什麼需要這份文件**：原開發團隊（IT）已不再投入本專案，前端匯出格式
因此無人維護。若日後有人調整前端，這份文件是判斷「什麼不能動」的唯一依據。
本文所有判定都附實測證據，不採信欄位名稱的字面意思。

**驗證樣本**：

| 樣本 | 版本 | 筆數 | 欄數 | 代表性 |
|------|------|------|------|--------|
| AHU-601 | 即時量測（每秒） | 228 | 669 | **臨時量測，非常態配置** |
| ZP 3-5_M1 | 長期量測（每 10 分） | 7 | 217 | 正式監測對象，accOA≈129 |
| CP 10_M1 | 長期量測（每 10 分） | 4 | 217 | 正式監測對象，accOA≈503（ZP 3-5 的 3.91 倍） |

**AHU-601 不具代表性**：它是臨時架設的量測，走每秒一筆的即時量測版；
正式監測對象是 ZP／CP 等泵浦與冰水主機，走每 10 分鐘一筆的長期量測版。
`data/rawdata.csv`（三軸原始值）也是 AHU-601 的，因此**所有以原始值反推
的感測器特性都只在該台的配置下成立**——見 `vibcore/config.py` 檔頭對適用
範圍的說明。凡是本文引用 AHU-601 的結論，都要看有沒有在泵浦上複驗過。

## 一、兩種匯出版本

前端有兩種輸出，**欄位數差很多**：

| | 即時量測 | 長期量測 |
|---|---|---|
| 取樣 | 每秒一筆 | 每 10 分鐘一筆 |
| 欄位數 | 669 | 217 |
| 諧波頻率（`accH01FREQ_x`…） | 有 | **無** |
| 諧波振幅（`accH01FREQ_V_x`…） | 有 | 有 |
| 合成軸諧波 / `_OA` 佔比 | 有 | **無** |
| `velH01~H10` | 有 | **無** |

正式運轉使用長期量測版。**歷史資料可能兩種混雜**（設備陸續換版，換版日期
各不相同），處理方式見 `docs/USAGE.md` §3.0 與 `--latest-cadence-only`。

即時量測版有一個容易誤導的特性：前端以 **10 秒滾動窗**計算，相鄰兩筆共用
90% 的原始資料。任何「穩定度」評估都會因此被高估，比較兩版本的統計量時
必須把這件事算進去。

## 二、目前使用中（19 欄）

見 `vibcore/config.py` 的 `AGG_SPEC`。

```
accRMS_x/y/z  accRMS  accPEAK  accCREST  accSKEW  accKURT
velRMS_x/y/z  velRMS  velPEAK  velOA
dispRMS  dispP2P  accOA
accMeanPeakFreq  accWeightedMeanFreq
```

### 合成軸欄位的可信度（已驗證）

| 欄位 | 合成方式 | 判定 |
|------|----------|------|
| `accRMS` | **精確等於三軸平方和開根** | 可信 |
| `velRMS` | **精確等於三軸平方和開根** | 可信 |
| `dispRMS` | 同上（受四捨五入影響） | 可信 |
| `accCREST` / `accKURT` | 落在三軸範圍外 | **可信**——比值與形狀統計量是對合成訊號另算，本來就不該等於三軸的任何函數 |
| `accOA` | **≈ 646 × accRMS**（見下） | 可用，但**不帶額外資訊** |

實測（ZP 3-5 第 1 列）：`accRMS_x/y/z` = 0.056/0.151/0.113 → 平方和開根
0.196，`accRMS` 欄正好是 0.196。CP 10 同樣吻合（0.784）。

### 兩個與絕對單位無關的關係（三台皆成立，可放心沿用）

| 關係 | 實測 |
|------|------|
| `accCREST = accPEAK / accRMS` | 三台相對誤差皆為 **0.00%** |
| `accOA ≈ 646 × accRMS` | 中位 643.2／649.9／643.3，逐筆比值 CV 僅 0.001~0.002，相關 0.998 |

第二項的意涵要記住：**`accOA` 只是 `accRMS` 的等比縮放，不帶額外資訊**。
兩者不可同時放進同一個多變量模型（會造成共線），目前
`vibcore.metrics.deviation` 用的特徵是 `vel_rms / acc_rms / acc_crest /
acc_kurt`，沒有踩到這個問題。早期文件寫的「accOA 約為三軸總和的
82~83%、定義未明」是另一個比較面向，與此不衝突。

## 三、已納入（2026-08 新增）

### 3.1 溫度 `tempMAX` / `tempAVG` / `tempMIN` → `temp_max/avg/min`

實測有值且有鑑別度：ZP 3-5 為 37.6°C，CP 10 為 50.6°C。

**價值**：這是唯一與振動獨立的物理通道。「振動變了但溫度沒變」與「兩者
一起變」對現場的意義不同，而做這個區分不需要推論成因，不違反本系統
「篩選而非診斷」的定位。

**待確認**：這是感測器內部溫度還是軸承座溫度。MEMS 加速度計通常回報晶片
溫度；若感測器貼在軸承座上，兩者有固定偏移但趨勢一致。**用於相對趨勢
（與自身基準比）不受影響，用於絕對門檻則需先釐清。**

### 3.1b `ISO10816_code` 的語意未經確認（2026-09 新增）

這個欄位的值是 1~4，但**沒人確認過它代表什麼分類體系**：

- 可能是 **ISO 2372 的 Class I~IV**（舊分類，依 kW 與基礎剛性）
- 也可能是 **ISO 10816-3 的 Group 1~4**（現行分類）

已知的矛盾線索：ZP 3-5 與 CP 10 都是泵、`ISO10816_code` 都填 2，
但 ISO 10816-3 的泵浦屬 Group 3/4，Group 2 是「中型機／馬達」。
要嘛工程師填的是舊的 Class II，要嘛是依驅動馬達而非依泵本身分類。

**更關鍵的是：就算群組確定了，Zone 判定還缺「基礎剛性」（rigid/flexible）
——前端資料完全沒有這個欄位，而同一群組下兩者的 A/B 界可差近一倍
（Group 2 為 1.40 vs 2.30）。**

因此系統預設把所有設備視為未分類，走相對基準與趨勢路徑。
要做「若假設是 X 會如何」的敏感度分析：

```bash
python -m validate.iso_readiness --data-dir data/ --compare
```

### 3.2 `iso10816` → `iso_zone_frontend`

前端已算好的 ISO 分級值（1 = Zone A）。

**交叉驗證通過**：ZP 3-5 的 velRMS 0.45、CP 10 的 0.68，依 Class II 的
A/B 界線 1.12 mm/s 判定皆為 Zone A，與前端的 `iso10816 = 1` 一致。

**用途**：作為本系統 ISO 判定的交叉檢查，不取代自行計算——前端假設的
機械等級未知。不一致時應觸發 `ISO_CLASS_SUSPECT`。

### 3.3 逐軸 `accCREST_x/y/z`、`accKURT_x/y/z` → 逐軸 max 與 median

衝擊型劣化常集中在單一方向，合成值會把它稀釋掉。實測 ZP 3-5 的三軸
crest 為 4.65/5.01/4.30，合成欄只有 4.08——低於任何一軸。

**但 kurtosis 的情況相反**：同一筆的三軸 kurt 是 3.15/3.37/2.87，合成欄
卻是 4.53，高於任一軸。所以逐軸值不必然比合成值敏感，兩者是不同的量，
規則應同時利用而非取代。

沿用既有的方向無關原則：**只取極值、不保留 x/y/z 標籤**（感測器可能
貼錯方向，見 `aggregate.py` 的 `_axis_energy_sorted`）。

**每小時聚合同時保留 max 與 median（2026-09）**：max 回答「這小時最尖的
一刻」，median 回答「這小時的代表性形狀」，規則判定用的是後者。
kurtosis 的業界判準（常態=3、>4 視為出現衝擊）講的是**一段訊號的峰度**，
不是 3600 個滾動窗峰度的最大值。實測 AHU-601 逐筆 accKURT 中位數 2.37、
僅 2.6% 超過 4，但每 30/60/114 筆取最大值後平均已達 7.17/13.49/19.00
（超過 4 的比例 14%/33%/50%），median 則不論區塊多大都穩定在 2.37。

這也是 `IMPACT_RISE` 移除 `kurt_absolute` 絕對門檻的原因——那道門檻套在
取最大值的 accKURT 上實測恆為真，AND 條件完全沒有把關。

### 3.4 尚未納入的其他逐軸欄位

## 四、不可用（120 欄）

### 4.1 諧波振幅 `accH01~H30 FREQ_V_x/y/z`（90 欄）

**確定不可用。** 三項獨立證據：

1. **跨設備不成比例**。CP 10 的整體振動是 ZP 3-5 的 3.91 倍，但兩者的
   30 階諧波能量和是 210.9 vs 223.8（**1.06 倍，等於沒動**）。同期
   TOP1-5 能量則是 20.2 → 133.2（6.6 倍，合理）。

2. **方向相反**。安靜的 ZP 3-5 的 H03 = 128.5，吵的 CP 10 只有 17.3。

3. **與整體位準零相關**。AHU-601（228 筆）逐軸諧波能量總和與該軸 `accOA`
   的相關係數僅 −0.06 ~ +0.13。若為同一訊號的頻譜分量，兩者必然同步變動。

即時量測版另有第四項證據：合成軸諧波振幅時常小於三軸中的任一軸
（H02 三軸 4.5/3.3/7.9，合成欄 2.2），振幅類的量不可能如此。

**注意**：頻率欄位（`accH01FREQ_x` 等）本身是準的——RPM 1710 → 轉速頻率
28.5 Hz，實測 H01 = 29.3（+2.8%）、H30 = 855.3（0.0%），確實鎖在轉速倍頻
上。早期文件寫「FREQ 峰值搜尋會鎖錯峰」是錯的。但**長期量測版沒有這些
頻率欄位**，且問題出在振幅而非頻率，故整組不使用。

### 4.2 主峰 `accTOP1~5 FREQ / FREQ_V_x/y/z`（30 欄）

**振幅合理，但頻率不適合單獨作為判定依據。**

振幅隨整體位準等比放大（見上），這部分是正常的。問題在主峰的「身分」
不穩定：

| 樣本 | TOP2/TOP1 振幅比 | TOP1 頻率標準差 |
|------|------------------|-----------------|
| AHU-601（每秒） | 0.21（主峰明顯） | 0.20 Hz |
| ZP 3-5（10 分） | 0.74 | 3.32 Hz |
| CP 10（10 分） | 0.86 | **95.45 Hz** |

泵類設備的前五個峰值振幅相差不到兩成，「誰是第一名」每次量測都在翻轉。

AHU-601 看似穩定是**滾動窗重疊造成的假象**（見 §一）。

未來若要使用，應以「前五個峰值的集合」（與排名無關）而非 TOP1 單點，
且需先驗證該設備的主峰是否具支配性。

## 五、已廢棄（17 欄）

原 IT 團隊以 SVM / DBSCAN 建置的健康分數與異常分類模型，本系統**不使用**。

```
HealthScore  Model_HealthScore  Model_FailureMode
FailureMode1~8_ConfidenceLevel
FailureMode1~8_Similarity
```

實測狀態不一致：AHU-601 全部為 0；ZP 3-5 的 `HealthScore` 為 92~95；
CP 10 為 0。分數本身難以判讀，且模型已無人維護。

**但 `ISO10816_code` 要保留。** 它雖然是當初為健康分數模型而請工程師
預先填寫、於資料載入時寫入，但**內容是工程師對機械等級的判斷，與模型
無關**。模型廢棄後這個欄位依然有效，而且正是 ISO 判定所需。

實測 ZP 3-5 與 CP 10 皆為 `ISO10816_code = 2`（Class II），並非早期
假設的「多數未設定（0）」。

## 六、前端不可變更的欄位

若日後調整前端，以下欄位**移除或改變語意會直接讓管線失效**：

| 欄位 | 用途 | 移除後果 |
|------|------|----------|
| `Time` | 時間戳 | 無法聚合，整條管線停擺 |
| `Name` | 設備識別 | 無法對應台帳 |
| `velRMS` | ISO 判定、運轉判定 | ISO 規則與運轉判定失效 |
| `velRMS_x/y/z` | 三軸分析 | 軸能量規則失效 |
| `accRMS`、`accRMS_x/y/z` | 多變量偏離的核心特徵 | STEP_CHANGE 失效 |
| `accCREST`、`accKURT` | 衝擊型指標 | IMPACT_RISE 失效 |
| `RPM` / `FMF` | 轉速參照 | 頻率相關判定失去基準 |
| `ISO10816_code` | 機械等級 | ISO Zone 判定退回「未分級」 |
| `Channel_X/Y/Z` | 量測點切分 | 量測點識別失準 |

`Label` 欄目前存的是電流 TAG 名稱，**本系統不使用**，可自由變更
（見 `validate/points.py`）。
