# 試跑計畫：驗證優先上線

> 版本：2026-10-11　狀態：草稿，供確認
>
> 背景：時程緊、專家能提供的意見有限、又擔心誤報。這份文件回答三件事：
> **現在能不能先上線、上線的是什麼、怎麼靠現場回饋逐步調整。**
> 數字來自 11 週真實資料的離線回測（65 個量測點、34 台設備、2026-06-05～08-20），
> 以及用合成資料逐日重放正式排程的結果；兩者都不是「真的壞了有沒有抓到」的證據（見 §七）。

---

## 一、結論

**可以先上線，上線的是「驗證」，不是「派工」。**

| 項目 | 判斷 | 依據 |
|---|---|---|
| 資料管線：讀檔 → 聚合 → 基準 → 14 條規則 → 入庫 → 自動結案 | **可以跑** | 55 天合成資料（植入事件）逐日走一遍正式排程；重放、第一天上線的模擬與第一份真實週報抓到 12 個回測看不到的問題並已修正（見 `DECISIONS` 〈上線前補洞〉）；自動測試 443＋59 項 |
| 週報 | **可以產出，不需要 Agent** | `python -m vibcore.reporting.cli`：版面上每個數字與每段文字都來自資料庫與規則引擎 |
| 派工 | **設備健康類不派工** | 只有「有外部標準可引用」與「系統事實」兩類會建立 Finding，其餘進觀察名單（§三） |
| 真的壞了抓不抓得到（召回） | **沒有證據** | 回測資料沒有被確認的故障標籤，無法計算；這是試跑要補的 |
| Agent 導讀 | **可以開始測，只給負責人看** | 診斷用語檢查（套用於 Agent 每個文字欄位）、總評下限、人員姓名去識別、數字白名單（report 模式）已實作並有自動測試；尚缺數字白名單強制模式、內容指紋、提示詞注入測試、題庫腳本（認證草稿第 4 張、§八之一） |
| 回覆管道（Dashboard） | **沒有** | 用試算表收集回饋（§五）；Finding 的 SLA 逾期數在試跑期沒有意義，不要當指標 |
| 對外寄信 | **關著** | SMTP 未設定；報告只落庫／存檔，由人轉交 |

為什麼敢說「不太會誤報」，又為什麼這句話只對一半：

- 設備健康類規則（衝擊性、突變、溫升、趨勢、頻譜、軸向）預設 `observe`：**不建 Finding、沒有 SLA、沒有人被指派**，
  只出現在週報的觀察名單。工程師不會因為它們白跑一趟。
- 但誤報的風險只是換了形式：從「白跑一趟」變成「名單太長沒人看」與「真的異常淹沒在名單裡」。
  **這正是試跑要量的東西**，不是已經解決的東西。

## 二、三個階段

| | 階段 1 · 影子 | 階段 2 · 試行 | 階段 3 · 正式 |
|---|---|---|---|
| 時間 | 約 2 週 | 約 4 週 | — |
| 誰收到報告 | 只有負責人（與 1～2 位判讀人員） | 加上設備工程師（只讀） | 依簽核鏈 |
| 派工 | 無 | 無；個別規則經回饋證明後才升 `warn` | 有，含 SLA |
| 主要目標 | 管線穩定、台帳到位、**量出各規則的雜訊率** | 工程師看得懂、肯回覆；調整門檻 | — |
| Agent 導讀 | 可測（只給負責人，§八之一） | 數字白名單強制、注入測試完成才開給工程師 | 同左 |

### 階段 1 · 影子（約 2 週）

做的事：每日排程照跑、每週產一份週報（無 Agent）、判讀人員用回饋表逐條標「真實／已知／雜訊／不確定」。

**進入階段 2 的條件**（全部成立）：

1. 連續 10 天以上排程成功、沒有無法解釋的失敗量測點（`vibcore.check` 與排程日誌）。
2. 至少產出並讀過 2 份週報。
3. 準備給工程師看的每條規則，已判 ≥ 10 件（回饋表 `score` 的「樣本不足」門檻）。
4. 雜訊率 ≥ 50% 的規則已處理：調高門檻、加下限、降為觀察、或停用（§六）。
5. 沒有已知的阻擋性缺陷。

### 階段 2 · 試行（約 4 週）

報告開放給工程師閱讀，回饋仍走試算表。**規則升級（`observe` → `warn`）的啟發式門檻**
（`validate.review_sheet score` 的建議欄用的同一組數字）：已判 ≥ 10 件、雜訊率 < 25%、
「真實＋已知」占比 ≥ 50%。這是建議不是自動決定——升級前先確認「真實」不全是「已知」
（已知的問題再派工沒有新資訊）。

### 階段 3 · 正式（不在本計畫範圍）

需要先有：回覆管道（Dashboard 或等價物）、Agent 護欄補齊（數字白名單強制、內容指紋、注入測試）、SMTP 或確定的轉交方式。
這份計畫不假設它們存在。

## 三、派工政策與預期數量

**政策**：只有兩類判定會建立 Finding（派工）；其餘一律進觀察名單。

1. **有外部標準可引用的**：`ISO_ZONE`、以及 ISO 錨定模式的 `VEL_HIGH`（額定功率 > 15 kW 且台帳有群組與基礎剛性）。
2. **系統事實**：`SENSOR_OFFLINE`、`DATA_QUALITY`、`ORIENTATION_CHANGE`、`SENSOR_SATURATION`、
   `STANDBY_NO_RUNTIME`、`ISO_CLASS_SUSPECT`。這些講的是資料與台帳是否可信，不是設備好壞。

沒有外部標準的 `VEL_HIGH`（額定 ≤ 15 kW 的泵、或未分級）退回相對基準 σ，並要求**實用顯著性**
（相對增幅 ≥ 25% 且絕對增幅 ≥ 0.10 mm/s），只進觀察名單。道理與整套系統一致：**沒有外部錨點就不派工**。

**11 週真實資料在這個政策下的樣子**（由 `episodes_detail.csv` 的 703 筆重新套用政策算出）：

| | 數量 | 說明 |
|---|---|---|
| 派工級（Finding） | 139 筆；平均 12.6 筆／週（0～34） | 91%（127 筆）是資料可用性，見下 |
| 　SENSOR_OFFLINE | 56 | 其中 42 筆集中在 4 天起算（7/25 一天 17 點）：共因中斷，不是 56 個獨立故障 |
| 　DATA_QUALITY | 71 | 91% 的可信資料佔比落在 0.35～0.5（門檻 0.5 的正下方）；約半數（36 筆）與同點位的離線事件前後 8 天內相連，其餘是獨立的資料缺漏；整體中位數持續 8 天、最長 77 天，不是一兩天的小事件 |
| 　ORIENTATION_CHANGE | 9 | 感測器方向／安裝改變 |
| 　ISO_CLASS_SUSPECT／SENSOR_SATURATION／STANDBY_NO_RUNTIME | 各 1 | |
| **設備健康類派工** | **0** | ISO_ZONE 0 筆；ISO 錨定的 VEL_HIGH 0 筆（機隊以 ISO 看是健康的，或不在 ISO 範圍） |
| 觀察名單 | 542 筆；週報每週約 54 項（21～111），涉及約 20／34 台 | 衝擊性 144、突變 246、溫升 106、VEL_HIGH 19、軸向 13、趨勢 9、頻譜 5；中位數只持續 1 天；前 10 台占 53% |

這張表要讀成兩件事：

- **派工那一側幾乎沒有設備健康的內容**——工程師收到的會是「感測器／資料有問題」與少量台帳／安裝事項。
  這對避免誤報是好事，但也代表系統目前**不會**主動說「這台泵要壞了」。
- **觀察名單才是設備健康訊號的所在，也是雜訊的所在。** 每週 54 項對讀者偏長；
  影子階段由判讀人員抽樣判定（回饋表每條規則取前 8 筆、同一設備最多 2 筆），不是逐項看完。

## 四、Day 0 檢查清單

**A. 基礎建設**

- [ ] 取得最新程式；`pip install -r requirements.txt`
- [ ] 資料庫：新庫直接 `db/schema.sql`。**既有的庫先跑 `python -m vibcore.check`，看【3b】列出的 ✗，只補套用那幾支**（`db/migration_00N_*.sql`，依編號順序；沒有 `psql` 就用 SQL 用戶端把整支檔案當一份腳本）。**已套用的不要重跑**：004 會把 IMPACT_RISE 與 ISO_ZONE／VEL_HIGH 的 `consecutive_readings` 重設為預設值。尤其要確認 **008**：舊庫缺它時，觀察級規則的嚴重度仍是 warn，會被當成要派工的事項
- [ ] 連線參數（`VIB_DB_*`）設好；補套用後再跑一次 `python -m vibcore.check`，確認【3b】全部 ✓、【4】沒有 `!`
- [ ] 每日排程設定完成（USAGE §4.3），**先手動跑一次確認**

**B. 台帳**

- [ ] 先跑一次每日排程讓設備依資料建立，再匯入台帳：`python -m vibcore.ledger_import --csv 台帳.csv --dry-run`，確認後去掉 `--dry-run`
- [ ] 台帳 id 只差空白／底線的（例：`CH01_M1` 對 `CH 01_M1`）**改台帳**；匯入工具會逐一列出，不會自動套用
- [ ] 請現場確認台帳的三件事（回測資料對照 SCADA 發現的）：
  ① CH01 的 device_id（台帳寫 `CH01_M1`，資料是 `CH 01_M1`）；
  ② CWP 04、CP 04 台帳標備機，但 SCADA 與振動都顯示約 80～90% 的時間在轉——是填錯，還是與主機輪替？
  輪替的話靜態旗標本身就不夠（§七第 6 點）；
  ③ CWP 05 台帳標非備機，但 SCADA 全零、振動水準落在備機那一群，實際很可能是備機
- [ ] `python -m vibcore.ledger_import` 結束時的覆蓋摘要：ISO 判定啟用的點數、額定 ≤ 15 kW 的點數（標準不適用，不是填錯）、標為備機的台數（0 台會有警告）

**C. 歷史資料與基準**

- [ ] 基準需要 14 天窗口內至少 168 小時可信資料，所以**上線第一天不要只餵當天的檔**：把最近 6～8 週的歷史 Analytic 檔放進資料夾，
  用 `--date <最新一天>` 跑一次，聚合與基準就位後，第一週才不是瞎的。多天的檔案會替每個有資料的日期補一筆匯入紀錄，
  所以第一份週報不會出現「匯入排程當天沒有執行」的警示；真的沒有資料進來的日子仍會被標出
- [ ] **不需要匯入 SCADA。** 日常排程與規則都不讀 SCADA（資料庫有表，但沒有匯入程式）；試跑只吃振動 Analytic CSV 與台帳。SCADA 匯出檔留著，離線分析工具需要時再用
- [ ] 這次載入會讓規則只看到「最新一天」的狀態（歷史上發生過什麼，回測已經回答過了），不會把整段歷史重放成一堆事項
- [ ] 備機（一天只跑一兩小時）建不出基準，只靠 `SENSOR_OFFLINE` 與 `STANDBY_NO_RUNTIME`——這是已知限制

**D. 報告與回饋**

- [ ] `python -m vibcore.reporting.cli --days 7 --out output/weekly.html --save` 能產出並打開
- [ ] 用回測 episodes 預演一次回饋表（影子階段開始前先量一次雜訊率）：
  `python -m validate.review_sheet export --episodes episodes_detail.csv --ledger 台帳.csv --out output/review_rehearsal.csv`

**E. 人**

- [ ] 指定負責人（看週報、決定調整）與 1～2 位判讀人員（填回饋表）
- [ ] 判讀人員讀過 `output/review_..._填寫說明.txt`（匯出時一併產生）

**F. 安全**

- [ ] SMTP 保持未設定；報告由人檢視後再轉交
- [ ] Agent 平台：不接，或依 §八之一 的條件接（只測不寄，產出由負責人檢視）
- [ ] 不在正式庫跑測試腳本（`test_rules.py`／`test_reporting.py` 會拒絕名稱不以 `_test` 結尾的庫）

## 五、每週作業

**每日**：排程自動跑（`python -m vibcore.pipeline.daily --data-dir <當日資料夾>`）；看結束時那行摘要，有失敗的量測點要追。

**每週一**（約 30 分鐘）：

```bash
# 1. 週報（不經 Agent）
python -m vibcore.reporting.cli --days 7 --out output/weekly_2026-W41.html --save

# 2. 本週待判定清單（Finding 與觀察名單）
python -m validate.review_sheet export --db --days 7 --out output/review_2026-W41.csv
```

3. 判讀人員在 `判定` 欄填 **真實／已知／雜訊／不確定**，`原因` 欄用標準詞（轉速負載、鄰機、備機停機、維修換件、
   感測器、通訊中斷、真實劣化、其他），有處置寫在 `處置` 欄。**不確定也是有效答案**——硬猜會污染雜訊率。

**每兩週**：

```bash
python -m validate.review_sheet score --sheets output/review_*.csv --csv output/review_score.csv
```

輸出每條規則的看過件數、四類占比、雜訊率與 80% 信賴區間、啟發式建議，以及雜訊的原因分布
（雜訊集中在「鄰機」或「轉速負載」時，該針對那一類處理，而不是整條規則調鬆）。
把結論與調整記在 `docs/DECISIONS_*.md`，下次比較才有基準。

## 六、調整手冊

規則的參數、啟停、嚴重度都在資料庫的 `rule_config`，**改了下一次排程就生效，不必改程式**
（2026-10 起正式排程才真的讀這些設定，見 USAGE §3.3）。先 `SELECT` 看現值再改。

| 症狀 | 做法 |
|---|---|
| 某條觀察類規則雜訊率 ≥ 50% | 調高它的門檻（`params`）；或 `is_active = FALSE` 先停掉；回饋表的原因欄會指出雜訊集中在哪一類 |
| VEL_HIGH 退回 σ 的觀察項太多 | 調高 `min_rel_change`／`min_abs_change`；或把 `fallback_severity` 維持 `observe`（預設） |
| 某條規則經回饋證明有用，想正式派工 | `UPDATE vib.rule_config SET severity = 'warn' WHERE rule_code = '…'`（先看 §二的升級門檻） |
| 週報太長 | 先看是不是集中在少數設備（前 10 台占 53%）：該設備是否備機未標、環境振動、轉速變動；修台帳比調門檻有效 |
| 資料可用性事項成串出現 | 先看是否同一天起算（共因中斷）；整批處理，不逐件追 |
| 同一台設備反覆出現在不同規則 | 多半是同一件事（工況或鄰機）被不同規則各抓一次，回饋表原因欄標「鄰機」或「轉速負載」 |

不要做的事：在沒有回饋證據時憑感覺放寬門檻——放寬後少掉的是不是雜訊，沒有人知道。

## 七、已知限制（誠實版）

1. **召回沒有證據。** 回測量的是「規則觸發了什麼」，不是「真的壞了有沒有抓到」。11 週資料沒有被確認的故障標籤，
   無法計算。試跑期間若現場有真實異常（維修、換件、停機檢查），請在回饋表的 `備註` 標出，這是唯一的召回線索來源。
2. **設備健康類目前不派工。** 見 §三。若 ISO 錨定的門檻一直不被觸及，系統在試跑期間的價值是觀察名單與資料可用性監測。
3. **觀察名單偏長且集中。** 每週約 54 項，前 10 台占 53%；中位數只持續 1 天，短事件占多數。
4. **資料可用性成串出現。** 56 筆 SENSOR_OFFLINE 有 42 筆在 4 天起算；目前每個點各開一件，尚未合併成一件「共因中斷」。
5. **額定 ≤ 15 kW 的泵不在 ISO 20816-3 範圍。** 只能看相對變化，且只進觀察名單。
6. **振動判定的「運轉」被鄰機傳導的振動污染。** SCADA 說停機而振動說在轉的機器，基準落在環境振動水準；
   `STANDBY_NO_RUNTIME` 對這些機器失效（回測只抓到 1 台）。以 SCADA 判運轉（決策紀錄 Q4 第二階段）**尚未建置**：
   沒有 SCADA 的匯入程式，規則也不讀 SCADA，所以現在匯入 SCADA 不會改變任何判定。
   它不是試跑的前置條件，但會改善 VEL_HIGH 觀察名單與備機監測；要不要提前由使用者決定。
7. **轉速對振動的影響只量了 velRMS。** 10 個轉速敏感點（其中 4 個在 ISO 範圍內）；衝擊性與溫升在這些點偏多
   （2.5×、1.9×）是否由轉速造成尚未驗證。
8. **沒有回覆管道。** Finding 狀態機（工程師回覆 → 主管 → 專家 → 結案）沒有介面可用；SLA 逾期數沒有意義。
   週報上的「逾期」標記照常顯示（未結案的事項超過 5 天沒人回覆就會標），試跑期請忽略；事項只會因為連續 3 天未再觸發而自動結案。
9. **Agent 護欄只完成一部分。** 已有診斷用語檢查、總評下限、姓名去識別、數字白名單（預設只回報不退回）；
   尚缺：數字白名單的強制模式（要先量誤退率）、內容指紋、提示詞注入測試、題庫腳本。見認證草稿第 4 張。
   因此 Agent 文字只給負責人看，不轉交給工程師。

## 八、與認證簡報第 8 張（Online 驗證）的對應

試跑期間**能**量到的：

| 第 8 張的項目 | 試跑能提供什麼 |
|---|---|
| 持續運行天數（門檻 > 14 天） | 影子階段的連續成功天數（無 Agent 的系統運行） |
| 嚴重事件誤報率 | 派工級事項在回饋表的雜訊比例（目前主要是資料可用性類） |
| 現場配合度 | 回饋表的回填率與逾期（以試算表為準，不是 Finding 狀態機） |
| 規則誤報 | 各規則的雜訊率與信賴區間 |

**不能**量到的（要等 Agent 測試跑過）：數字正確率、診斷性斷言件數、導讀判讀一致性、週報彙整時間減少。
這些欄位維持【待實測】，不用無 Agent 的試跑數字填；Agent 測試蒐集到的數字見 §八之一。

## 八之一、Agent 導讀測試（影子階段內進行，只有負責人看）

不經 Agent 的週報（`vibcore.reporting.cli`）仍是正式產出；Agent 導讀是**疊在上面的一層**，
測它不影響派工與週報本身。

**開始前**

- [ ] 影子階段的排程已穩定（`vibcore.check` 全過、近期無無法解釋的失敗量測點）
- [ ] SMTP 保持未設定；`send_report` 只落庫，產出的報告由負責人在資料庫或存檔中檢視，不轉交
- [ ] Agent 平台的提示詞貼自 `docs/agent_prompt_weekly.md`（含〈系統會檢查你寫的內容〉一節）；工具清單為 `docs/agent_tools.md` 的 8 支 API，不加其他工具
- [ ] 環境變數 `VIB_GUARDRAIL_NUMBERS` 維持預設 `report`（要改成 `enforce` 之前先量誤退率，見下）
- [ ] 每日寄送上限（`VIB_REPORT_DAILY_LIMIT`，預設 3）不要調高：測試要重送時 429 是正常的

**測的方式**

1. 每週（影子階段通常是 2 份）讓 Agent 照提示詞跑一次，負責人逐份對照 `不經 Agent 的週報` 檢視。
2. 把〈設定時的檢查清單〉（`agent_prompt_weekly.md` 末）全跑一次，其中總評下限與 422 重送兩項要在測試環境刻意製造。
3. 統計稽核紀錄（`audit_log`）：
   - `send_report_rejected` 件數與 `reason`（`diagnostic_language`／`unverified_numbers`）
   - `send_report` 的 `n_unverified_tokens`、`verdict_adjusted`
4. 每個未核對的數字人工看一眼，分成「誤報（Agent 引用正確、白名單比不到）」與「真的改寫」。
   前者是調整比對規則的依據，後者是 Agent 提示詞要補的。

**什麼時候可以把數字白名單切成 `enforce`**：已累積足夠多份 Agent 輸出（建議 ≥ 8 份，涵蓋日報與週報），
誤報（正確引用卻被判未核對）占全部被擋項目的比例低到可以接受，並且比對規則已針對誤報型態調整過。
這是判斷不是公式；做完在決策紀錄記下數字與理由。

**什麼時候可以開給工程師看**：以上全數完成，且——

- 診斷性斷言件數 0（被退回的不算進報告，但要看退回的原因分佈）
- 嚴重度降級件數 0（`verdict_adjusted` 為 true 的比例不為 0 時，回頭看是提示詞還是模型的問題）
- 數字白名單已在 `enforce`，連續多份沒有被退回
- 提示詞注入測試完成（尚未建置）
- 內容指紋（尚未建置）

**停用條件**：連續 2 期被退回（任何原因），或發現一份已落庫的導讀含診斷性斷言——先停用 Agent、保留不經 Agent 的週報，
找出原因再決定。

## 九、停止條件

出現以下任一情況就暫停，先找原因：

- 排程連續 2 天失敗，或同一批量測點連續失敗
- 週報出現明顯不合理的內容（例如全廠同時大量「新發現」——先看是不是補跑／重放造成的時鐘問題或資料夾放錯）
- 判讀人員反映看不懂或不信任（比雜訊率更早的訊號）
- 現場發生真實異常，而系統沒有任何對應的觀察項或事項——這是召回的反例，優先記錄並分析
